Hard Rock Concierge Flow

A chat concierge for Hard Rock Hotel Miami that checks bookings, makes bookings and reads the guest's Unity by Hard Rock points balance. It uses three MCP servers. They have no auth now. WSO2 gateway proxies add authentication and per-tool authorization in a later phase.

Open decisions

  1. Whose token reaches the gateway. Either the guest's own Thunder token (scopes follow the guest) or the agent's own client token (scopes follow the agent). This changes what sub the gateway sees.
  2. Binding member_id to the caller. The servers trust the member_id argument. Even in phase 2, a token with bookings:read can read any member's bookings unless the gateway maps a claim into the request or the server reads X-Forwarded-Authorization.
  3. Gateway to server reachability. The servers run on the Mac and the gateway runs in k3d. Earlier notes say the cluster reaches the Mac at 192.168.5.2, not host.k3d.internal. I'll re-check this before phase 2.

Not part of this design: step-up authentication. A call that's missing a scope fails, and nothing escalates it.
